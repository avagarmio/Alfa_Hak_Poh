# Техническое задание: Модуль безопасности персональных данных

Автоматическая проверка включает два обязательных этапа: (1) проверку качества кода загруженного решения и (2) нагрузочное тестирование развёрнутого решения.

---

## 1. Краткое описание

В Банке в связи с активным развитием генеративного искусственного интеллекта разрабатывается множество продуктов для клиентов и сотрудников, генерирующих большой объем запросов к LLM. По требованиям информационной безопасности Банка критически важно защищать персональные данные при обращении к LLM.

* **Задача:** разработать сервис (Модуль безопасности персональных данных), выполняющий детекцию типов персональных данных, их маскирование в исходящих запросах к LLM и демаскирование в получаемых ответах.


* **Цель:** создать высоконагруженный и быстрый сервис в роли прокси Core-компонента.


* **Целевая аудитория трека:** LLM/AI-инженеры, Backend/Frontend-разработчики, UX/UI-дизайнеры, продакт-менеджеры, аналитики, Data Scientists/ML-инженеры, специалисты по банковским процессам и безопасности данных.



---

## 2. Полное описание

### Проблематика

В текущий момент каждая команда Банка решает задачу защиты ПД изолированно, что порождает ряд проблем:

* Решения спроектированы под частные требования и не обладают достаточной гибкостью в настройке маскирования.


* Демаскирование реализовано лишь частично.


* Отсутствует должная отказоустойчивость под высокой нагрузкой.


* Разрозненные решения сложно переиспользовать, что приводит к нерациональным трудозатратам.



### Образ решения

Необходимо реализовать приложение, перехватывающее и обрабатывающее запросы от систем-потребителей к LLM и ответы модели.

Критерии оценки решения:

* Точность выявления персональных данных, запрещенных к открытой передаче.


* Минимальный уровень ложных срабатываний (False Positive).


* Сохранение семантического контекста запроса для качественной работы AI-модели.


* Возможность гибкого управления правилами в разрезе систем-потребителей.


* Простота подключения новых систем.


* Поведение при сбоях и недоступности зависимостей (деградация/отказоустойчивость).


* Отсутствие утечек исходных ПД в логах и технических метриках.


* Масштабируемость архитектуры для добавления новых правил и сущностей без рефакторинга ядра.



---

## 3. Ключевые требования

* Бесшовное встраивание в контур взаимодействия «система-потребитель $\leftrightarrow$ LLM».


* Полное покрытие обязательного перечня типов персональных данных.


* Строгое соответствие стандартам безопасности, шифрования и минимизации данных согласно нормам РФ и ЦБ РФ.


* Отсутствие критических ошибок при обработке и обеспечение точности результата.


* Жесткое соблюдение SLA по стабильности, доступности и задержкам ответов.



---

## 4. Функциональные требования

### 4.1. Идентификация типов персональных данных

Сервис обязан однозначно определять следующие типы ПД:

* ФИО;


* Дата рождения;


* Место рождения;


* Гражданство;


* Серия и номер паспорта;


* Кем выдан паспорт (орган, выдавший документ);


* Код подразделения;


* Дата выдачи паспорта;


* Серия и номер водительского удостоверения;


* Адрес (включая раздельные сущности: страна, индекс, город, улица, дом, квартира и т.д.);


* Номер мобильного/городского телефона;


* Адрес электронной почты (Email);


* ИНН;


* Номер платёжной банковской карты;


* Срок действия и имя держателя карты;


* CVV/CVC-код карты;


* ПИН-код карты.



Дополнительные условия идентификации:

* **Фильтрация ложных срабатываний:** отделение общеупотребимых сущностей от персональных данных (например, «Александр Пушкин» или адрес отделения Банка не должны маскироваться).


* **Регистронезависимость:** детекция должна корректно отрабатывать вне зависимости от регистра символов.


* **Расширяемость:** возможность беспрепятственного добавления новых типов сущностей.


* **Аудит:** логирование найденных типов ПД для каждого запроса без логирования самих значений.



### 4.2. Маскирование

Поддержка вариативности написания данных:

* Различные регистры;


* Различные форматы дат (числовые: `дд.мм.гггг`, `гггг.дд.мм`, `мм.дд.гггг` и текстовые: «12 мая 1995 года»);


* Наличие текстовых разделителей сущностей (например, «серия ХХХХ номер ХХХХХХ»).



### 4.3. Демаскирование

Восстановление исходных данных из замаскированного текста с точным соблюдением расположения знаков и структуры.

### 4.4. Общие требования

* Детализированное сквозное логирование этапов обработки без утечки защищаемых данных.


* Экспорт технических метрик: Latency, RPS, TPS (tokens per second).


* Контроль доступа: разграничение доступа только для зарегистрированных систем-потребителей.


* Конфигурация под системы:
* Включение/выключение доступа для конкретной системы;


* Настройка списка типов ПД для детекции и маскирования под систему;


* Включение/выключение демаскирования для системы;


* Наличие краткой инструкции по конфигурированию объемом **не более 5 предложений**.




* Качество работы: целевой порог точности детекции, маскирования и демаскирования — **не менее 95%**.


* Поддержка объемных текстов: обработка до **100 000 токенов** в рамках одного запроса.



---

## 5. Нефункциональные требования

* **Безопасность:** обработка в изолированном защищенном контуре в соответствии со стандартами ИБ Банка.


* **Надежность:** graceful degradation при сбоях внешних сервисов, идемпотентная обработка, информативные коды ошибок.


* **Производительность:** задержка (Latency) $\le$ 1 секунды при пропускной способности $\ge$ 1000 RPS.


* **Масштабируемость:** горизонтальное масштабирование сервиса без деградации Latency.



---

## 6. Дополнительные преимущества (бонусы)

* Реализация токенизации/детокенизации либо подмены ПД синтетическими правдоподобными данными.


* Гибкий выбор стратегии (маскирование / токенизация / синтетика) на уровне настроек системы.


* Удержание нагрузки **2000 RPS** при соблюдении Latency $\le$ 1 секунды.


* Детекция дополнительных удостоверений личности помимо паспорта РФ.


* Правила составной маскировки (маскирование только при наличии связки сущностей, например: отдельный «пин-код» не трогается, но комбинация «номер карты + пин-код» подлежит маскированию).

## 7. Регламент автоматической проверки решений

Для зачета решения необходимо успешно пройти обе проверки: проверку исходного кода и нагрузочный тест.

### 7.1. Проверка качества кода

Решение загружается исключительно в формате `.zip`.
Правила формирования архива:

* Разрешено включать только исходный код и конфигурационные файлы.


* **Запрещено:** прикладывать скомпилированные бинарники, дампы, датасеты, медиафайлы.


* **Запрещено:** упаковывать каталоги зависимостей (`node_modules`, `venv`, `env`) и директории сборки (`target`, `build`, `dist`, `bin`, `out`, `obj`, `.git`, `.idea`, `__pycache__`, `coverage`).



### 7.2. Нагрузочное тестирование

Тестирование развернутого сервиса осуществляется платформой AlfaSonar по эталонному датасету.

* **Сетевой протокол:** HTTP или HTTPS (допускаются self-signed сертификаты, проверка идет с флагом `ssl_verify=false`).


* **Таймаут:** 10 секунд на запрос (превышение считается ошибкой).


* **Ретраи:** проверяющая система делает до 2 повторных попыток на запрос (всего до 3 обращений). Эндпоинт обязан быть идемпотентным.


* **Обработка статуса 429 (Too Many Requests):** допускается при перегрузке. Сервис должен отдавать заголовок `Retry-After`. Если 429 не проходит при повторах, запрос фиксируется как отказ под нагрузкой.


* **Условие останова (Circuit Breaker):** 5 невалидных ответов подряд (5xx, таймаут, неверная схема) полностью останавливают процесс тестирования (статус 429 ошибкой не считается).


* **Профиль нагрузки:** ~5 минут на полном датасете с целевой планкой в 1000 RPS и ориентиром Latency $\le$ 1 сек.

## Приложение А. Контракт API `/process`

Единый HTTP-эндпоинт, реализующий логику прямого (маскирование) и обратного (демаскирование) шага на базе ключа корреляции `payload_id`:

* **Первый запрос с новым `payload_id` (маскирование):** в поле `payload` передается исходный текст. Сервис сохраняет состояние по `payload_id` и возвращает замаскированный результат.


* **Второй запрос с тем же `payload_id` (демаскирование):** в поле `payload` передается ранее возвращенная замаскированная строка. Сервис возвращает исходный незамаскированный текст.


* **Формат ответа всегда идентичен:** `{"result": "<строка>"}`.



### OpenAPI 3.0.3 Спецификация (`process_api.yaml`)

```yaml
openapi: 3.0.3
info:
  title: Модуль безопасности ПД контракт /process
  version: "1.0.0"
  description: |
    Единый контракт, который команды-участники ДОЛЖНЫ реализовать на своём сервисе.
    Система проверки AlfaSonar обращается к этому эндпоинту для нагрузочного тестирования
    и оценки точности маскирования/демаскирования персональных данных.
servers:
  - url: https://your-solution.example.com
    description: HTTPS (self-signed допускается проверка идёт с ssl_verify=false)
  - url: http://your-solution.example.com
    description: HTTP также поддерживается
paths:
  /process:
    post:
      operationId: process
      summary: Маскирование/демаскирование строки (коррелируется по payload_id)
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/ProcessRequest"
      responses:
        "200":
          description: Успешная обработка
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/ProcessResponse"
        "429":
          description: Слишком много запросов. Допустимо под нагрузкой.
        "4XX":
          description: Ошибка запроса
        "5XX":
          description: Внутренняя ошибка сервиса
components:
  schemas:
    ProcessRequest:
      type: object
      required: [payload, payload_id]
      properties:
        payload:
          type: string
          description: Исходная строка (шаг 1) либо ранее замаскированная строка (шаг 2).
          example: "Клиент Иванов Иван Иванович, паспорт 4509 123456"
        payload_id:
          type: string
          description: Идентификатор корреляции пары маскирование/демаскирование.
          example: "8a77d363c7c044b49b41d7b8a448243a"
    ProcessResponse:
      type: object
      required: [result]
      properties:
        result:
          type: string
          description: Результат обработки.
          example: "Клиент И. И. И., паспорт 45** ****56"

```

## Приложение В. Инструкция по нагрузочному тестированию

### Оценка метрик

* **Прямой шаг:** выданная маска сравнивается с эталонной разметкой датасета на основе нормированного span-based расстояния Левенштейна в диапазоне $[0..1]$.


* **Обратный шаг:** демаскированная строка посимвольно сверяется с оригинальной строкой датасета.



### Самопроверка доступности и формата контракта

Для валидации схемы обмена доступен публичный тестовый стенд:

```bash
curl -X POST https://process-test.holydev.space/process \
  -H "Content-Type: application/json" \
  -d '{"payload": "тестовая строка", "payload_id": "selfcheck-1"}'

```
